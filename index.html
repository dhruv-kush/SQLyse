      SQL Injection Fundamentals

      Understand the weakness
      behind unsafe queries.

      SQL injection can occur when untrusted input influences a database query. Understanding how this behaviour appears helps developers identify risky query construction and apply stronger defensive controls.

      01

      What is SQL Injection?

      SQL injection is a class of vulnerability in which untrusted input can alter the intended structure or behaviour of a database query. The weakness is created by unsafe query construction, not by the input alone.

      02

      How It Happens

      Risk increases when applications combine values directly with query text, handle input inconsistently or connect with excessive database privileges.

      User Input Application Query Database Response

      03

      Common Categories

      Different response patterns can suggest that input is influencing a query. Each signal requires careful verification.

      01

      Error-based behaviour

      Database-related error patterns may appear when an application processes unexpected input.

      02

      Boolean-response differences

      Controlled input variations may produce repeatable differences in content or application flow.

      03

      Time-based behaviour

      Consistent timing changes may indicate backend query influence, but latency must be ruled out.

      04

      Union/query-structure manipulation

      Unexpected result shapes may suggest that input is affecting the structure of a data request.

      04

      Potential Impact

      If a weakness is confirmed, the resulting impact depends on application design, database permissions and exposed data.

      • Authentication controls may be bypassed
      • Data could be accessed without authorisation
      • Stored information may be modified
      • Records could be lost or made unavailable
      • Database structure may be exposed
      • Broader application compromise could become possible

      05

      Primary defence

      Defensive Controls

      Layered controls reduce the chance that untrusted values can change query intent and limit the impact if a defect reaches production.

      Parameterised queries

      Keep SQL command text separate from values supplied by users.

      Prepared statements

      Define query structure first and bind each value through the database driver.

      Server-side validation

      Enforce expected types, lengths and formats before data reaches the query layer.

      Generic error handling

      Store detailed failures in protected logs and return neutral messages to clients.

      Least-privilege accounts

      Give application database identities only the operations and records they require.

      Security regression testing

      Continuously verify query boundaries and unusual input throughout delivery.

      Secure framework or ORM usage

      Use safe binding APIs correctly and review any raw-query escape hatches.

      06

      Vulnerable vs Safer Query Construction

      Conceptual pseudocode illustrates the trust boundary without providing an attack sequence.

      Unsafe concept

      Query text is assembled directly using a user-controlled value.

      queryText = concatenate(
  queryStructure, userControlledValue)
      Safer concept

      SQL structure remains fixed while the value is passed separately as a parameter.

      queryText = fixedStructure
boundValues = [userControlledValue]

      About the Product

      From target input
      to actionable findings.

      SQLyse brings crawling, input discovery, response analysis and security reporting into one focused interface.

      01

      What SQLyse Does

      SQLyse is designed to organise a controlled application-security review. Detection is evidence-led and potential findings remain subject to human verification.

      • Accept a target URL
      • Crawl reachable application pages
      • Discover forms and input parameters
      • Send controlled test inputs
      • Compare application responses
      • Detect suspicious SQL-related behaviour
      • Organise potential findings
      • Provide remediation guidance
      • Generate reports

      02

      Scanner Workflow

      A single review path carries target context from initial discovery into a reportable finding record.

      1. Target

        Validate the application URL and establish scan context.

      2. Crawl

        Follow reachable routes within the permitted target scope.

      3. Discover

        Identify forms, parameters and other user-controlled inputs.

      4. Test

        Apply controlled variations without destructive probe behaviour.

      5. Analyze

        Compare status, length, timing and sanitised response signals.

      6. Report

        Organise cautious findings, evidence and remediation guidance.

      03

      Core Capabilities

      The interface is structured around the evidence and review tasks needed during a focused SQL injection assessment.

      01

      Application crawling

      Map reachable routes within the defined target boundary.

      02

      Form and parameter discovery

      Record the inputs that may influence server-side behaviour.

      03

      Response comparison

      Evaluate controlled variations across safe response metadata.

      04

      SQL error-family detection

      Group sanitised database error patterns for review.

      05

      Severity classification

      Prioritise potential findings using evidence and confidence.

      06

      Finding review

      Preserve technical context and human verification status.

      07

      Remediation guidance

      Connect observed behaviour with concise defensive controls.

      08

      JSON, CSV and PDF reporting

      Generate structured exports through the connected backend report service.

      04

      Integration Architecture

      Architecture

      The frontend communicates with the Flask API, which coordinates scanning, analysis, findings and report generation.

      Frontend Flask API Crawler Scanner Response Analyzer Finding Generator Report Service

      05

      Scope and Limitations

      Automated signals support investigation; they do not replace secure engineering review or authorised manual validation.

      • Human review remains essential.Potential findings require technical verification before classification.
      • No finding is not proof of security.Coverage limits and application behaviour can leave weaknesses undetected.
      • Application access affects coverage.Dynamic and authenticated areas may require future session support.
      • Response differences need context.Normal application branching can produce false-positive signals.
      • Permission defines the boundary.SQLyse should only assess systems the operator is authorised to test.
